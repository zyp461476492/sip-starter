# 基本呼叫流程

一句话：**一条 INVITE 穿过代理到达 UAS，经 1xx 进展响应、最终 2xx 建立对话，
ACK 确认，BYE 拆除**。这是全部 SIP 知识的汇合点，其他概念都是它的零件。

## 全景（原文）

> When a user agent client desires to initiate a session (for example,
> audio, video, or a game), it formulates an INVITE request.  The
> INVITE request asks a server to establish a session.  This request
> may be forwarded by proxies, eventually arriving at one or more UAS
> that can potentially accept the invitation.
（RFC 3261 §13.1）

> Before sending a final response, the UAS can also send provisional
> responses (1xx) to advise the UAC of progress in contacting the called
> user.
（RFC 3261 §13.1）

> A 2xx response to an INVITE establishes a session, and it also
> creates a dialog between the UA that issued the INVITE and the UA
> that generated the 2xx response.  Therefore, when multiple 2xx
> responses are received from different remote UAs (because the INVITE
> forked), each 2xx establishes a different dialog.  All these dialogs
> are part of the same call.
（RFC 3261 §13.1）

最后这段是理解 [[concepts/dialog]]（待建）与 forking 的关键：**一通呼叫可以有多个对话**。

## 消息序列（F1–F14）

原文示例见 §24.2 的 Figure 1（"SIP session setup example with SIP trapezoid"，见 §4），
拓扑与路由示例见 §16.12.1.1 Basic SIP Trapezoid。

| 序 | 消息 | 方向 | 要点 |
|---|---|---|---|
| F1 | INVITE | Alice → atlanta.com 代理 | 带 SDP（`Content-Type: application/sdp`） |
| F2 | 100 Trying | 代理 → Alice | 属于 INVITE 事务的 provisional，非可靠传输 |
| F6 | INVITE | 代理 → 代理 | 代理逐跳追加 Via（原文示例里能看到三层 Via） |
| F7 | 180 Ringing | 代理 → 代理 | 业务侧"振铃"，同样 1xx |
| F10/F11 | 200 OK | 逐跳回送 | 携带 SDP 应答与 `To: tag`，**建立对话** |
| F12 | ACK | Alice → Bob | 2xx 的 ACK 由 UAC core 生成，**不属于 INVITE 事务** |
| F13 | BYE | Bob → Alice | 对话内请求 |
| F14 | 200 OK | Alice → Bob | 结束对话 |

F1 原文（§24.2）：

```
INVITE sip:bob@biloxi.com SIP/2.0
Via: SIP/2.0/UDP pc33.atlanta.com;branch=z9hG4bKnashds8
Max-Forwards: 70
To: Bob <sip:bob@biloxi.com>
From: Alice <sip:alice@atlanta.com>;tag=1928301774
Call-ID: a84b4c76e66710
CSeq: 314159 INVITE
Contact: <sip:alice@pc33.atlanta.com>
Content-Type: application/sdp
Content-Length: 142
```

F7 的响应里已经出现 `To: Bob <sip:bob@biloxi.com>;tag=a6c85cf`——**响应侧补上 tag，对话才完整**（§24.2）。

## ACK 的两套规则（最易错处）

> Once it receives a final response, the UAC needs to send an ACK for
> every final response it receives.  The procedure for sending this ACK
> depends on the type of response.  For final responses between 300 and
> 699, the ACK processing is done in the transaction layer and follows
> one set of rules (See Section 17).  For 2xx responses, the ACK is
> generated by the UAC core.
（RFC 3261 §13.1）

- 3xx–6xx 的 ACK：**事务层**做，复用 INVITE 的 branch
- 2xx 的 ACK：**UAC core** 做，是新的一个"自成事务"（详见 [[concepts/transaction]]）

## 这个流程串起来的东西

- [[concepts/transaction]]：F1–F2 的阶段重传、F10 之后 2xx 的重传、ACK 的事务归属
