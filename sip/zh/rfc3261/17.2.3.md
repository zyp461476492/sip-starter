当服务端从网络上收到一个请求时，必须把它匹配到一个已存在的事务。做法如下。

先看请求顶层 Via 头域里的 branch 参数。若它存在且以魔法 cookie `z9hG4bK` 开头，则该请求是由符合本规范的客户端事务生成的，因此该 branch 参数在该客户端发出的所有事务之间唯一。满足下列条件时，请求匹配某个事务：

1. 请求里的 branch 参数等于创建该事务的那个请求顶层 Via 头域里的 branch 参数，且

2. 请求顶层 Via 里的 sent-by 值等于创建该事务的那个请求里的 sent-by 值，且

3. 请求的方法与创建该事务的那个请求的方法一致；ACK 除外——此时创建该事务的请求的方法应为 INVITE。

这条匹配规则对 INVITE 事务与非 INVITE 事务同样适用。

> sent-by 值被用作匹配过程的一部分，是因为不同客户端可能偶然或恶意地使用相同的 branch 参数。

若顶层 Via 头域里的 branch 参数不存在、或不含魔法 cookie，则改用下列流程。它们存在是为了与符合 RFC 2543 的实现向后兼容。

当 Request-URI、To tag、From tag、Call-ID、CSeq 与顶层 Via 头域都与创建该事务的那个 INVITE 请求相同时，该 INVITE 请求匹配该事务。此时，该 INVITE 是创建该事务的那个原 INVITE 的重传。当 Request-URI、From tag、Call-ID、CSeq 号（不含方法）与顶层 Via 头域都与创建该事务的那个 INVITE 请求相同，且该 ACK 的 To tag 与服务端事务发出的响应的 To tag 相同时，该 ACK 请求匹配该事务。匹配依据各头域各自定义的匹配规则进行。把 To 头域里的 tag 纳入 ACK 匹配过程，有助于在代理处区分“对 2xx 的 ACK”与“对其他响应的 ACK”——该代理可能已把两种响应都转发出去（这种情形会在异常条件下出现：具体来说，当一个代理分叉了一个请求后崩溃，响应可能被投递给另一个代理，后者最终可能向上游转发多个响应）。若某 ACK 请求匹配到某个 INVITE 事务，而该事务此前已被另一 ACK 匹配过，则该 ACK 视为前一 ACK 的重传。

对其他所有请求方法，当 Request-URI、To tag、From tag、Call-ID、CSeq（含方法）与顶层 Via 头域都与创建该事务的那个请求相同时，该请求匹配该事务。匹配依据各头域各自定义的匹配规则进行。当非 INVITE 请求匹配到一个已存在的事务时，它就是创建该事务的那个请求的重传。

由于匹配规则里含 Request-URI，服务端无法把响应匹配到事务。当 TU 把响应交给服务端事务时，它必须交给该响应所针对的那个具体的服务端事务。
