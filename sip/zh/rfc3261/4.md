本节用简单的例子介绍 SIP 的基本操作。本节是教程性质的，**不包含任何规范性陈述**。

第一个例子展示了 SIP 的四项基本功能：定位端点、表达通信意愿、协商会话参数以建立会话，以及会话建立之后的拆除。

图 1 是 Alice 与 Bob 两个用户之间一次典型 SIP 消息交换。（每条消息用字母 “F” 加编号标注，供正文引用。）在这个例子里，Alice 用她 PC 上的一个 SIP 应用（称为软电话，softphone）通过 Internet 呼叫 Bob 的 SIP 电话。图中还画了两台 SIP 代理服务器，分别代表 Alice 和 Bob 促成会话建立。这种典型布局因图 1 中虚线的几何形状而得名 “SIP 梯形（SIP trapezoid）”。

Alice 用 Bob 的 SIP 身份来“呼叫”他，那是一种称为 SIP URI 的统一资源标识符（URI）。SIP URI 定义在 §19.1，形式与电子邮件地址相似，通常包含用户名和主机名。此处是 `sip:bob@biloxi.com`，其中 `biloxi.com` 是 Bob 的 SIP 服务提供商的域。Alice 自己的 SIP URI 是 `sip:alice@atlanta.com`。Alice 可能是手工输入 Bob 的 URI，也可能是点了超链接或通讯录里的一项。SIP 还提供一种安全 URI，称为 SIPS URI，例如 `sips:bob@biloxi.com`。对 SIPS URI 发起呼叫，保证承载全部 SIP 消息的传输从主叫到被叫所在域之间是安全的加密传输（即 TLS）；从被叫的域再往被叫，请求同样是安全发送的，但所用安全机制取决于被叫域的策略。

SIP 基于类似 HTTP 的请求/响应事务模型。每个事务由一次请求（在服务器上调用某个特定方法，即某个功能）和至少一个响应构成。本例中，事务始于 Alice 的软电话向 Bob 的 SIP URI 发送一个 INVITE 请求。INVITE 是 SIP 方法的一个例子，它指明请求方（Alice）希望服务器（Bob）执行什么动作。INVITE 请求里带有一组头域（header field）——头域是具名属性，提供关于该消息的附加信息。INVITE 中出现的头域包括：呼叫的唯一标识、目的地址、Alice 的地址，以及 Alice 希望与 Bob 建立何种会话的信息。图 1 中的消息 F1（INVITE）大致如下：

```
                     atlanta.com  . . . biloxi.com
                 .      proxy              proxy     .
               .                                       .
       Alice's  . . . . . . . . . . . . . . . . . . . .  Bob's
      softphone                                        SIP Phone
         |                |                |                |
         |    INVITE F1   |                |                |
         |--------------->|    INVITE F2   |                |
         |  100 Trying F3 |--------------->|    INVITE F4   |
         |<---------------|  100 Trying F5 |--------------->|
         |                |<-------------- | 180 Ringing F6 |
         |                | 180 Ringing F7 |<---------------|
         | 180 Ringing F8 |<---------------|     200 OK F9  |
         |<---------------|    200 OK F10  |<---------------|
         |    200 OK F11  |<---------------|                |
         |<---------------|                |                |
         |                       ACK F12                    |
         |------------------------------------------------->|
         |                   Media Session                  |
         |<================================================>|
         |                       BYE F13                    |
         |<-------------------------------------------------|
         |                     200 OK F14                   |
         |------------------------------------------------->|
         |                                                  |

         Figure 1: SIP session setup example with SIP trapezoid
```

```
      INVITE sip:bob@biloxi.com SIP/2.0
      Via: SIP/2.0/UDP pc33.atlanta.com;branch=z9hG4bK776asdhds
      Max-Forwards: 70
      To: Bob <sip:bob@biloxi.com>
      From: Alice <sip:alice@atlanta.com>;tag=1928301774
      Call-ID: a84b4c76e66710@pc33.atlanta.com
      CSeq: 314159 INVITE
      Contact: <sip:alice@pc33.atlanta.com>
      Content-Type: application/sdp
      Content-Length: 142

      (Alice's SDP not shown)
```

文本编码的消息，第一行是方法名（INVITE），其后各行是头域列表。本例只包含**最小必需集合**。下面简要说明这些头域：

- **Via** 包含 Alice 期望接收本请求响应的地址（`pc33.atlanta.com`），还包含标识本事务的 `branch` 参数。
- **To** 包含显示名（Bob）和请求最初指向的 SIP 或 SIPS URI（`sip:bob@biloxi.com`）。显示名的语法见 RFC 2822 [3]。
- **From** 同样包含显示名（Alice）和标明请求发起者的 SIP 或 SIPS URI（`sip:alice@atlanta.com`）。该头域还有一个 `tag` 参数，装着软电话加上的随机串（`1928301774`），用于识别。
- **Call-ID** 包含本次呼叫的全局唯一标识，由随机串和软电话的主机名或 IP 地址组合生成。**To 的 tag、From 的 tag 与 Call-ID 三者合在一起，完整定义 Alice 与 Bob 之间一个对等的 SIP 关系**，这个关系称为对话（dialog）。
- **CSeq**（Command Sequence）包含一个整数和一个方法名。对话内每发一个新请求，CSeq 号加一，它是传统的序列号。
- **Contact** 包含一个 SIP 或 SIPS URI，代表直连 Alice 的一条路径，通常由“用户名 @ 完全限定域名（FQDN）”构成。虽然首选 FQDN，但许多终端系统并没有注册域名，因此也允许使用 IP 地址。**Via 头域告诉其他要素把响应发到哪里，Contact 头域则告诉其他要素把将来的请求发到哪里。**
- **Max-Forwards** 用于限制请求在去往目的地的途中可以经过的跳数。它是个整数，每跳减一。
- **Content-Type** 描述消息 body 的类型（本例的 body 未显示）。
- **Content-Length** 给出消息 body 的字节数。

完整的 SIP 头域集合见 §20。

会话的细节——例如媒体类型、编解码器、采样率——不用 SIP 描述。SIP 消息的 body 用某种其他协议的格式描述会话，其中一种格式是会话描述协议（SDP，RFC 2327 [1]）。本例中未显示的这条 SDP 消息，由 SIP 消息承载的方式，类似于电子邮件携带附件、HTTP 消息携带网页。

由于软电话并不知道 Bob 的位置，也不知道 biloxi.com 域里 SIP 服务器在哪，软电话把 INVITE 发往为 Alice 所在域 atlanta.com 服务的 SIP 服务器。atlanta.com 这台 SIP 服务器的地址，可以事先配置在 Alice 的软电话里，也可以通过 DHCP 之类的机制发现。

atlanta.com 这台 SIP 服务器属于一种称为**代理服务器**（proxy server）的 SIP 服务器。代理服务器接收 SIP 请求，并代表请求方将其转发出去：它收到 INVITE 后，先向 Alice 的软电话回一个 100 (Trying) 响应，表示 INVITE 已收到、代理正在替她把 INVITE 路由到目的地。SIP 的响应用三位数字的状态码加一句描述性短语表示。该响应里的 To、From、Call-ID、CSeq 以及 Via 中的 `branch` 参数都与 INVITE 相同，Alice 的软电话据此把这个响应与先前发出的 INVITE 对上号。接着 atlanta.com 代理通过某种 DNS 查询（可能是一种专门用来查找某域 SIP 服务器的查询）定位 biloxi.com 上的代理服务器，这一步见 [4]（RFC 3263）。拿到 biloxi.com 代理的 IP 地址后，它把 INVITE 转发（proxies）过去。**转发之前，atlanta.com 代理会在消息里追加一个 Via 头域值，内容是它自己的地址**（原有的第一个 Via 是 Alice 的地址）。biloxi.com 代理收到 INVITE，回一个 100 (Trying) 给 atlanta.com 代理，表示已收到、正在处理，然后去查一个泛称为**位置服务**（location service）的数据库，里面存着 Bob 当前的 IP 地址（这个数据库怎么填，下一节会看到）。biloxi.com 代理同样追加一个含自身地址的 Via 头域值，再把 INVITE 代理给 Bob 的 SIP 电话。

Bob 的 SIP 电话收到 INVITE 后向 Bob 提示来电，让 Bob 决定是否接听，也就是电话铃响。Bob 的 SIP 电话用一个 180 (Ringing) 响应表示这件事，该响应沿原路经两台代理反向送回。**每个代理都用 Via 头域决定响应往哪里送，并把自己那条地址从顶部删掉。** 因此，尽管最初的 INVITE 需要 DNS 与位置服务查找才能路由，180 (Ringing) 却不需要任何查找、也不需要代理维护状态就能回到主叫。这还带来一个很有用的性质：**看到 INVITE 的每个代理，也会看到针对该 INVITE 的所有响应。**

Alice 的软电话收到 180 (Ringing) 后把这个信息转达给 Alice，可能用音频回铃音，也可能在屏幕上显示提示。

本例中 Bob 决定接听。他拿起话筒时，他的 SIP 电话发送一个 200 (OK) 响应，表示呼叫已被接听。这个 200 (OK) 带有消息 body，里面是用 SDP 描述的、Bob 愿意与 Alice 建立的会话类型。于是 SDP 消息是**两阶段**交换：Alice 发了一份给 Bob，Bob 又回了一份给 Alice。这种两阶段交换提供基本的协商能力，基于 SDP 的简单 offer/answer 模型。如果 Bob 不想接听，或者正在另一通电话上，那么发出去的就会是错误响应而不是 200 (OK)，结果是不建立任何媒体会话。SIP 响应码完整列表见 §21。Bob 发出的 200 (OK)（图 1 中的消息 F9）大致如下：

```
      SIP/2.0 200 OK
      Via: SIP/2.0/UDP server10.biloxi.com
         ;branch=z9hG4bKnashds8;received=192.0.2.3
      Via: SIP/2.0/UDP bigbox3.site3.atlanta.com
         ;branch=z9hG4bK77ef4c2312983.1;received=192.0.2.2
      Via: SIP/2.0/UDP pc33.atlanta.com
         ;branch=z9hG4bK776asdhds ;received=192.0.2.1
      To: Bob <sip:bob@biloxi.com>;tag=a6c85cf
      From: Alice <sip:alice@atlanta.com>;tag=1928301774
      Call-ID: a84b4c76e66710@pc33.atlanta.com
      CSeq: 314159 INVITE
      Contact: <sip:bob@192.0.2.4>
      Content-Type: application/sdp
      Content-Length: 131

      (Bob's SDP not shown)
```

响应的第一行是响应码（200）和 reason phrase（OK），其余各行是头域。**Via、To、From、Call-ID 和 CSeq 都是从 INVITE 请求里复制过来的**（这里有三个 Via 头域值：Alice 的 SIP 电话加的一个、atlanta.com 代理加的一个、biloxi.com 代理加的一个）。Bob 的 SIP 电话给 To 头域加了一个 `tag` 参数。这个 tag 会被两个端点都写进对话，并出现在本次呼叫后续所有请求与响应中。Contact 头域给出一个 URI，通过它可以直接找到 Bob 的 SIP 电话。Content-Type 与 Content-Length 指的是消息 body（未显示），其中含有 Bob 的 SDP 媒体信息。

除了本例所示的 DNS 与位置服务查找，代理服务器还可以做灵活的“路由决策”，决定把请求发往何处。例如若 Bob 的 SIP 电话回了 486 (Busy Here)，biloxi.com 代理可以把 INVITE 代理给 Bob 的语音信箱服务器。代理还可以同时把一个 INVITE 发往多个位置，**这种并行搜索称为分叉（forking）**。

本例中，200 (OK) 沿两台代理送回 Alice 的软电话；软电话停止回铃音，提示呼叫已接通。最后 Alice 的软电话向 Bob 的 SIP 电话发送确认消息 ACK，确认已收到最终响应（200 (OK)）。本例中 ACK 由 Alice 的软电话直接发给 Bob 的 SIP 电话，**绕过了两台代理**——因为两个端点已经通过 INVITE/200 (OK) 交换，从 Contact 头域学到了彼此的地址，而这个地址在最初发 INVITE 时还是未知的。两台代理做过的查找不再需要，于是代理退出本次呼叫流程。至此完成用来建立 SIP 会话的 INVITE/200/ACK 三方握手。会话建立的完整细节见 §13。

Alice 与 Bob 的媒体会话就此开始，他们用 SDP 交换中商定的格式发送媒体包。一般说来，端到端的媒体包走的是与 SIP 信令消息不同的路径。

会话期间，Alice 或 Bob 任一方都可以决定改变媒体会话的特征，办法是发送一个带新媒体描述的 re-INVITE。re-INVITE 引用已有的对话，让对方知道这是要修改既有会话而非建立新会话。对方回 200 (OK) 表示接受该变更，请求方再用 ACK 回应这个 200 (OK)。若对方不接受变更，则发送诸如 488 (Not Acceptable Here) 的错误响应，这个响应同样会收到一个 ACK。**但 re-INVITE 失败并不会导致既有呼叫失败**——会话继续使用先前协商好的特征。会话修改的完整细节见 §14。

通话结束时 Bob 先挂断，产生一个 BYE 消息。这个 BYE 直接发往 Alice 的软电话，同样绕过了代理。Alice 用 200 (OK) 确认收到 BYE，会话与 BYE 事务就此结束。**这里不发送 ACK**——只在响应 INVITE 请求的响应时才发 ACK。这种对 INVITE 特殊处理的原因后面再讲，它与 SIP 的可靠性机制、电话振铃到被接听可能耗时很久、以及分叉有关。也正因如此，SIP 里的请求处理常被划分为 **INVITE** 与 **非 INVITE（non-INVITE）** 两类，后者指 INVITE 之外的所有方法。会话终止的完整细节见 §15。

有些情况下，让 SIP 信令路径上的代理在整个会话期间看到端点之间的全部消息是有用的。例如 biloxi.com 代理若希望在最初的 INVITE 之后继续留在 SIP 消息路径上，它就在 INVITE 里加一个必需的、称为 Record-Route 的路由头域，其值是一个能解析到该代理的主机名或 IP 地址的 URI。这条信息会由 Bob 的 SIP 电话收到，也会（因为 Record-Route 头域在 200 (OK) 中被回送）由 Alice 的软电话收到，并在对话存续期间保存。于是 biloxi.com 代理就能收到并代理 ACK、BYE 以及 BYE 的 200 (OK)。**每个代理都可以独立决定是否接收后续消息**，那些消息会经过所有选择接收的代理。这个能力常被用来支撑通话中的（mid-call）业务。

注册（registration）是 SIP 里另一种常见操作。注册是 biloxi.com 服务器得知 Bob 当前位置的方式之一。Bob 的 SIP 电话在初始化时以及之后按周期，向 biloxi.com 域中一台称为 SIP 注册服务器（registrar）的服务器发送 REGISTER 消息。REGISTER 消息把 Bob 的 SIP 或 SIPS URI（`sip:bob@biloxi.com`）与它当前登录的那台机器（用 Contact 头域里的 SIP 或 SIPS URI 表示）关联起来。注册服务器把这条关联（也称为绑定，binding）写入一个称为位置服务的数据库，供 biloxi.com 域内的代理使用。一个域的注册服务器常与该域的代理部署在同一处。**重要概念：SIP 服务器类型之间的区别是逻辑上的，不是物理上的。**

Bob 不限于只从一台设备注册：他家中的 SIP 电话和办公室的那台都可以发注册。这些信息一起存进位置服务，使代理可以用多种方式搜索来定位 Bob。同理，一台设备上也可以同时有多个用户注册。

位置服务只是一个抽象概念。它一般存放这样的信息：代理输入一个 URI，得到零个或多个 URI，告诉代理把请求发往何处。注册是生成这类信息的一种方式，但不是唯一方式。管理员可以按自己意愿配置任意的映射函数。

最后要注意：**在 SIP 里，注册用于路由入向（incoming）SIP 请求，对出向请求的授权没有任何作用**。授权与认证在 SIP 中要么按请求逐条用 challenge/response 机制处理，要么使用 §26 讨论的底层机制。
