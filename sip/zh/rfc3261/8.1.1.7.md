Via 头域指明本事务所用的传输，并标识响应应当发往的位置。**只有先选定通往下一跳将要使用的传输之后，才加入一个 Via 头域值**（这一步可能用到 [4] 里的过程）。

UAC 创建请求时，**MUST** 在该请求中插入一个 Via。头域中的协议名与协议版本 **MUST** 分别为 `SIP` 和 `2.0`。Via 头域值 **MUST** 包含 `branch` 参数，该参数用来标识由该请求创建的事务，客户端与服务端双方都会用到它。

该 UA 发出的所有请求，其 `branch` 参数值 **MUST** 在时间与空间上唯一。此规则的例外是非 2xx 响应对应的 CANCEL 与 ACK：如下文所述，CANCEL 请求的 `branch` 参数值与被它取消的那个请求相同；如 §17.1.1.3 所述，非 2xx 响应对应的 ACK 也使用它所确认的那个 INVITE 的同一 `branch` ID。

> 原文旁注：`branch` ID 参数之所以要求唯一、以便充当事务 ID，这一点在 RFC 2543 中并没有。

遵循本规范的要素插入的 `branch` ID，**MUST** 始终以字符 `"z9hG4bK"` 开头。这 7 个字符用作魔术 cookie（magic cookie，取 7 位是因为足以保证旧有的 RFC 2543 实现不会碰巧取到这样的值），于是收到请求的服务器就能判定该 `branch` ID 是按本规范所述方式构造的（也就是全局唯一）。除此之外，`branch` token 的具体格式由实现自行决定。

Via 的 `maddr`、`ttl` 与 `sent-by` 各组成部分由传输层在处理请求时填写（§18）。

代理对 Via 的处理见 §16.6 第 8 项与 §16.7 第 3 项。

> 译注：最容易记错的两点——① `branch` 唯一性的两个例外（CANCEL、非 2xx 的 ACK）恰好是“必须与原请求同事务”的两种消息；② `z9hG4bK` 是**前缀**而不是完整值，看到 `z9hG4bKnashds7` 时 `z9hG4bK` 之后才是实现自己生成的串。
