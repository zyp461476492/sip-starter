SIP 请求与响应的区别在于：请求的起始行是 Request-Line。Request-Line 包含方法名、Request-URI 和协议版本，各元素之间用一个空格（SP）分隔。

Request-Line 以 CRLF 结束。除行尾的 CRLF 序列外，不允许出现 CR 或 LF；任何元素内部都不允许出现线性空白（LWS）。

```
      Request-Line  =  Method SP Request-URI SP SIP-Version CRLF
```

**Method**：本规范定义六个方法：REGISTER 用于注册联系信息；INVITE、ACK 与 CANCEL 用于建立会话；BYE 用于终止会话；OPTIONS 用于查询服务器的能力。由标准轨 RFC 记载的 SIP 扩展可以定义其他方法。

**Request-URI**：Request-URI 是 §19.1 所述的 SIP 或 SIPS URI，或某个通用 URI（RFC 2396 [5]）。它指出本请求所指向的用户或服务。Request-URI 中 **MUST NOT** 出现未转义的空格或控制字符，且 **MUST NOT** 用 `<>` 括起来。

SIP 要素 **MAY** 支持 `"sip"` 与 `"sips"` 之外的 scheme，例如 RFC 2806 [9] 的 `"tel"` URI scheme。SIP 要素 **MAY** 用任何可用的机制转换非 SIP URI，得到 SIP URI、SIPS URI 或别的 scheme。

**SIP-Version**：请求与响应消息都带有正在使用的 SIP 版本，并在版本排序、兼容性要求与版本号升级这几件事上遵循 [H3.1]（把其中的 HTTP 换成 SIP、HTTP/1.1 换成 SIP/2.0）。为符合本规范，发送 SIP 消息的应用 **MUST** 携带值为 `"SIP/2.0"` 的 SIP-Version。SIP-Version 字符串大小写不敏感，但实现 **MUST** 发送大写形式。

与 HTTP/1.1 不同，SIP 把版本号当作字面字符串处理。实践中这不该造成任何差别。
