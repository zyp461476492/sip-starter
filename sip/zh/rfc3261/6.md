以下术语对 SIP 有特殊含义。

**Address-of-Record**：address-of-record（AOR）是一个 SIP 或 SIPS URI，它指向一个带位置服务的域，该位置服务能把该 URI 映射到用户可能可达的另一 URI。通常，位置服务的内容由注册填充。AOR 常被理解为用户的“公开地址”。

**Back-to-Back User Agent**：背靠背用户代理（B2BUA）是一个逻辑实体，它收到请求后以服务端（UAS）的身份处理它。为了判定该请求应如何应答，它同时充当客户端（UAC）并生成请求。与代理服务器不同，它维护对话状态，并且必须参与它已建立的那些对话上发出的所有请求。由于它就是 UAC 与 UAS 的拼接，其行为无须再单独定义。

**Call**：call 是口语用语，指对等体之间的某种通信，通常为多媒体对话而建立。

**Call Leg**：对话（dialog）的另一个名字 [31]；本规范已不再使用。

**Call Stateful**：若一个代理从发起对话的 INVITE 一直保留状态到终止该对话的 BYE 请求，它就是 call stateful 的。call stateful 代理一定是 transaction stateful 的，但反过来不一定成立。

**Client**：客户端是任何发送 SIP 请求、接收 SIP 响应的网络元素。客户端可能与人直接交互，也可能不。用户代理客户端与代理都是客户端。

**Conference**：包含多个参与者的多媒体会话（见下文 session）。

**Core**：core 指某一特定类型 SIP 实体所特有的功能集，即：有状态代理、无状态代理、用户代理或注册服务器各自特有的部分。除无状态代理的 core 以外，所有 core 都是事务用户（transaction user）。

**Dialog**：对话是两个 UA 之间一段时间内持续存在的对等 SIP 关系。对话由 SIP 消息建立，例如对 INVITE 请求的 2xx 响应。对话由 call identifier、local tag 与 remote tag 标识。对话在 RFC 2543 中曾被称为 call leg。

**Downstream**：事务内消息转发的方向之一，指请求从用户代理客户端流向用户代理服务器的方向。

**Final Response**：终止一个 SIP 事务的响应；与之相对的临时响应则不终止事务。所有 2xx、3xx、4xx、5xx 与 6xx 响应都是最终响应。

**Header**：header 是 SIP 消息的组成部分，用于承载关于该消息的信息。它由一串头域构成。

**Header Field**：头域是 SIP 消息头（header）的组成部分。一个头域可以出现为一行或多行头域行。头域行由头域名与零个或多个头域值构成。同一头域行上的多个头域值以逗号分隔。有些头域只能有一个头域值，因此总是只出现为一行头域行。

**Header Field Value**：头域值（header field value）是单个值；一个头域由零个或多个头域值构成。

**Home Domain**：为某个 SIP 用户提供服务的域。通常就是该用户注册的 address-of-record 中 URI 里的域。

**Informational Response**：等同临时响应（provisional response）。

**Initiator, Calling Party, Caller**：用 INVITE 请求发起会话（及对话）的一方。从发出建立对话的首个 INVITE 起，直到该对话终止，主叫方一直保持这一角色。

**Invitation**：一个 INVITE 请求。

**Invitee, Invited User, Called Party, Callee**：为建立新会话而接收 INVITE 请求的一方。从收到该 INVITE 起，直到该 INVITE 所建立对话终止，被叫方一直保持这一角色。

**Location Service**：位置服务供 SIP 重定向服务器或代理服务器查询被叫方可能的位置。它含一份 binding 列表，把 address-of-record 键映射到零个或多个联系地址。binding 可以经由多种方式创建与删除；本规范定义 REGISTER 方法来更新 binding。

**Loop**：一个到达某代理、被转发、后又回到同一代理的请求。它第二次到达时，Request-URI 与第一次相同，影响代理行为的其他头域也未变，因此代理会对它做出与第一次相同的处理决定。被环回的请求属于错误；检测与处理它们的流程由协议规定。

**Loose Routing**：若一个代理遵循本规范定义的 Route 头域处理流程，就称它是松散路由（loose routing）的。这些流程把请求的目的地（在 Request-URI 里）与沿途需要经过的代理集合（在 Route 头域里）分开。符合这套机制的代理也称为 loose router。

**Message**：SIP 元素之间作为协议数据发送的数据。SIP 消息要么是请求，要么是响应。

**Method**：方法是请求意图在服务端上调用的主要功能。方法承载在请求消息本身里。方法举例：INVITE 与 BYE。

**Outbound Proxy**：出向代理（outbound proxy）是即便不是由 Request-URI 解析出来的那个服务端、也仍从客户端接收请求的代理。通常 UA 被手工配置一个出向代理，或通过自动配置协议得知一个。

**Parallel Search**：在并行搜索（parallel search）中，代理收到一个来向请求后，向多个可能的用户位置同时发出若干请求。与顺序搜索那样“先发一个、等最终响应后再发下一个”不同，并行搜索发请求时不等先前请求的结果。

**Provisional Response**：服务端用来表示进展、但不终止 SIP 事务的响应。1xx 响应是临时响应，其他响应都视为最终响应。

**Proxy, Proxy Server**：代理（服务器）是一种中介实体，它同时充当服务端与客户端，以代替其他客户端发请求。代理服务器主要承担路由角色，即它的职责是确保请求被送到“更接近”目标用户的另一个实体。代理也用于执行策略（例如确认某个用户获准发起呼叫）。代理会解读请求消息、必要时在转发前重写其中的特定部分。

**Recursion**：客户端对 3xx 响应做递归（recurse），是指它向该响应 Contact 头域里的一个或多个 URI 生成新请求。

**Redirect Server**：重定向服务器是一个用户代理服务器，它对自己收到的请求生成 3xx 响应，指示客户端去联系另一组 URI。

**Registrar**：注册服务器（registrar）是接受 REGISTER 请求、并把其中收到的信息放进它所管理的域的位置服务的服务器。

**Regular Transaction**：regular transaction 指方法为 INVITE、ACK、CANCEL 以外任何方法的事务。

**Request**：从客户端发往服务端的 SIP 消息，用于调用某个特定操作。

**Response**：从服务端发往客户端的 SIP 消息，用于表明客户端先前发给服务端的某个请求的状态。

**Ringback**：回铃音（ringback）是主叫方应用产生的信令音，表示被叫方正被提醒（振铃）。

**Route Set**：路由集是一组有序的 SIP 或 SIPS URI，表示发送某个特定请求时必须经过的代理列表。路由集可以通过 Record-Route 之类的头域学到，也可以通过配置得到。

**Server**：服务端是接收请求以便为其服务、并把响应发回给那些请求的网络元素。服务端的例子有代理、用户代理服务器、重定向服务器与注册服务器。

**Sequential Search**：在顺序搜索（sequential search）中，代理服务器依次尝试每个联系地址，只有当前一个地址产生了最终响应，才处理下一个。2xx 或 6xx 类的最终响应总是终止顺序搜索。

**Session**：取自 SDP 规范：“多媒体会话是一组多媒体发送方与接收方，以及从发送方流向接收方的数据流。多媒体会议是多媒体会话的一个例子。”（RFC 2327 [1]）（按 SDP 的定义，一个 session 可以包含一个或多个 RTP session。）按此定义，被叫方可以被不同的多通 call 多次邀请到同一个 session。若使用 SDP，则 session 由 origin 字段里的 SDP user name、session id、network type、address type 与 address 元素拼接定义。

**SIP Transaction**：SIP 事务发生在客户端与服务端之间，包含从客户端发给服务端的第一个请求起、直到服务端发给客户端的最终（非 1xx）响应为止的所有消息。若该请求是 INVITE 且最终响应为非 2xx，则该事务还包含对那个响应的 ACK。对 INVITE 请求的 2xx 响应的 ACK 属于另一个独立的事务。

**Spiral**：螺旋（spiral）是指被路由到某代理、又被转发出去、随后再次到达同一代理的 SIP 请求，但这一次在某个方面有所不同，使得代理做出与原先不同的处理决定。通常这意味着该请求的 Request-URI 与此前到达时不同。与 loop 不同，spiral 不是错误状态。常见成因是呼叫前转：用户呼叫 joe@example.com，example.com 代理把它转给 Joe 的 PC，Joe 的 PC 再把它转给 bob@example.com。这个请求又被代理回 example.com 代理。但它不是 loop：因为该请求指向另一个用户，所以视为 spiral，是合法状态。

**Stateful Proxy**：有状态代理是一个逻辑实体，它在处理请求的过程中维护本规范定义的客户端与服务端事务状态机，也称 transaction stateful 代理。有状态代理的行为在 §16 进一步定义。(transaction) stateful 代理与 call stateful 代理不是一回事。

**Stateless Proxy**：无状态代理是一个逻辑实体，它处理请求时不维护本规范定义的客户端或服务端事务状态机。无状态代理把它收到的每个请求都向下游转发，把收到的每个响应都向上游转发。

**Strict Routing**：若一个代理遵循 RFC 2543 及本 RFC 许多此前的工作草案版本的 Route 处理规则，就称它是严格路由（strict routing）的。那条规则会导致代理在有 Route 头域时破坏 Request-URI 的内容。本规范不采用严格路由行为，改用松散路由行为。执行严格路由的代理也称为 strict router。

**Target Refresh Request**：对话内发出的 target refresh request 定义为可以修改该对话远端目标的请求。

**Transaction User (TU)**：位于事务层之上的那一层协议处理。事务用户包括 UAC core、UAS core 与 proxy core。

**Upstream**：事务内消息转发的方向之一，指响应从用户代理服务器流回用户代理客户端的方向。

**URL-encoded**：按 RFC 2396 §2.4 [5] 编码的字符串。

**User Agent Client (UAC)**：客户端（UAC）是这样一个逻辑实体：它创建新请求，然后用客户端事务状态机把它发出去。UAC 的角色只在该事务存续期间有效。换句话说，若某软件发起了一个请求，它在该事务存续期间充当 UAC；若它随后收到一个请求，则处理那个事务时它转为用户代理服务器角色。

**UAC Core**：UAC 所需的、位于事务层与传输层之上的那套处理功能。

**User Agent Server (UAS)**：服务端（UAS）是这样一个逻辑实体：它对 SIP 请求生成响应。该响应接受、拒绝或重定向该请求。该角色只在该事务存续期间有效。换句话说，若某软件对一个请求作出响应，它在该事务存续期间充当 UAS；若它随后生成一个请求，则处理那个事务时它转为用户代理客户端角色。

**UAS Core**：UAS 侧所需的、位于事务层与传输层之上的那套处理功能。

**User Agent (UA)**：既能充当客户端、又能充当服务端的逻辑实体。

UAC 与 UAS 的角色，以及代理与重定向服务器的角色，都是逐个事务界定的。例如，发起呼叫的用户代理在发出初始 INVITE 请求时充当 UAC，而在收到被叫方的 BYE 请求时充当 UAS。同样地，同一套软件可以对一个请求充当代理服务器，对下一个请求充当重定向服务器。

上面定义的代理、位置服务与注册服务器都是逻辑实体；实现 MAY 把它们合进一个应用里。
