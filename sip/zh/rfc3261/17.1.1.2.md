INVITE 客户端事务的状态机见图 5。当 TU 用 INVITE 请求发起一个新客户端事务时，MUST 进入初始状态 “calling”。客户端事务 MUST 把该请求交给传输层发送（见 §18）。若使用不可靠传输，客户端事务 MUST 以 T1 为值启动定时器 A。若使用可靠传输，客户端事务 SHOULD NOT 启动定时器 A（定时器 A 管的是请求重传）。无论何种传输，客户端事务 MUST 以 64*T1 秒为值启动定时器 B（定时器 B 管的是事务超时）。

定时器 A 到期时，客户端事务 MUST 把请求交给传输层重传，且 MUST 以 2*T1 为值重置该定时器。在事务层的语境里，重传的形式化定义是：把先前已交给传输层的消息再交给传输层一次。

2*T1 秒后定时器 A 再次到期时，请求 MUST 被再次重传（前提是客户端事务仍处于该状态）。此过程 MUST 持续下去，使请求的重传间隔逐次翻倍。这些重传 SHOULD 只在客户端事务处于 “calling” 状态时进行。

T1 的默认值为 500 ms。T1 是对客户端事务与服务端事务之间 RTT 的估计值。在不允许接入通用互联网的封闭私有网络中，元素 MAY 使用更小的 T1 值（不过这是 NOT RECOMMENDED）。T1 MAY 选得更大——若事先已知 RTT 更大（例如在高延迟接入链路上），这是 RECOMMENDED 的。无论 T1 取何值，本节描述的重传指数退避 MUST 采用。

若定时器 B 到期时客户端事务仍处于 “Calling” 状态，客户端事务 SHOULD 通知 TU 已发生超时。客户端事务 MUST NOT 生成 ACK。64*T1 的值等于在不可靠传输下发出七个请求所需的时间。

若客户端事务在 “Calling” 状态下收到临时响应，则转入 “Proceeding” 状态。在 “Proceeding” 状态下，客户端事务 SHOULD NOT 再重传请求。此外，该临时响应 MUST 被交给 TU。此后任何临时响应也 MUST 在 “Proceeding” 状态下交给 TU。

处于 “Calling” 或 “Proceeding” 状态时，收到状态码为 300–699 的响应 MUST 使客户端事务转入 “Completed”。客户端事务 MUST 把收到的响应交给 TU，且 MUST 生成 ACK 请求（即使传输是可靠的也一样；由响应构造 ACK 的准则见 §17.1.1.3），然后把 ACK 交给传输层发送。ACK MUST 发往原请求所发往的同一地址、端口与传输。客户端事务 SHOULD 在进入 “Completed” 状态时启动定时器 D：使用不可靠传输时取值至少 32 秒，使用可靠传输时取值为零秒。定时器 D 反映的是使用不可靠传输时服务端事务可能停留在 “Completed” 状态的时长。它等于 INVITE 服务端事务中的定时器 H（默认 64*T1）。不过，客户端事务并不知道服务端事务实际使用的 T1 值，因此这里不用 T1 推导定时器 D，而是取绝对下限 32 秒。

处于 “Completed” 状态时收到的任何最终响应重传，MUST 使 ACK 被再次交给传输层重传，但新收到的响应 MUST NOT 被交给 TU。响应重传的定义是：按 §17.1.3 的规则会匹配到同一客户端事务的任何响应。

若定时器 D 在客户端事务处于 “Completed” 状态时到期，客户端事务 MUST 转入 terminated 状态。

处于 “Calling” 或 “Proceeding” 状态时，收到 2xx 响应 MUST 使客户端事务进入 “Terminated” 状态，并且该响应 MUST 被交给 TU。该响应的处理取决于 TU 是 proxy core 还是 UAC core：UAC core 会处理为它生成 ACK，而 proxy core 总是把 200 (OK) 向上游转发。代理与 UAC 对 200 (OK) 的处理方式不同，正是它不在事务层处理的原因。

客户端事务 MUST 在进入 “Terminated” 状态的那一刻被销毁。这其实是保证正确运行所必需的。原因是：对 INVITE 的 2xx 响应受到特殊对待——每一个都要由代理转发，而 UAC 里对 ACK 的处理也不同。因此每个 2xx 都需要既交给 proxy core（以便转发）、又交给 UAC core（以便确认）。其中不发生任何事务层处理。每当传输层收到一个响应，若传输层按 §17.1.3 的规则找不到匹配的客户端事务，该响应就直接交给 core。由于匹配的客户端事务被第一个 2xx 销毁，后续 2xx 找不到匹配，于是就会交给 core。
