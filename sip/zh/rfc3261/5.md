SIP 被组织成一个分层协议，意思是它的行为按一组相当独立的处理阶段来描述，阶段之间只是松散耦合。之所以把协议行为按层描述，是为了便于呈现——把各元素共有的功能只在一节里讲完。这种描述方式并不以任何方式规定实现。当我们说某个元素“含”某一层时，意思是它符合该层定义的那套规则。

并非协议规定的每个元素都含每一层。此外，SIP 规定的元素是逻辑元素，不是物理元素。一个物理实现可以选择充当不同的逻辑元素，甚至逐个事务地切换。

SIP 最底层是它的语法与编码。编码用扩展巴科斯-瑙尔范式（BNF）规定。完整的 BNF 在 §25；SIP 消息结构的概览见 §7。

第二层是传输层。它规定客户端如何发送请求、接收响应，以及服务端如何从网络上接收请求、发送响应。所有 SIP 元素都含传输层。传输层见 §18。

第三层是事务层。事务是 SIP 的基本构件。一个事务，指客户端事务（经传输层）发给服务端事务的一个请求，以及服务端事务回给客户端的所有针对该请求的响应。事务层负责应用层重传、响应与请求的匹配，以及应用层超时。客户端（UAC）完成的任何任务，都是靠一连串事务完成的。关于事务的讨论见 §17。用户代理含事务层，有状态代理也含；无状态代理不含事务层。事务层有一个客户端部分（称为客户端事务）与一个服务端部分（称为服务端事务），两者各由一个有限状态机表示，该状态机是为处理某个特定请求而构造的。

事务层之上那一层称为事务用户（TU）。除无状态代理以外，每个 SIP 实体都是事务用户。当 TU 想发送请求时，它创建一个客户端事务实例，并把请求连同要发往的目的 IP 地址、端口与传输一并交给它。创建客户端事务的 TU 也可以取消它。当客户端取消一个事务时，它要求服务端停止进一步处理、回退到该事务发起之前的状态，并针对该事务生成一个特定的错误响应。这件事用 CANCEL 请求完成——CANCEL 自身构成一个事务，但引用着要取消的那个事务（§9）。

SIP 元素，即客户端与服务端、无状态代理与有状态代理、以及注册服务器，都含一个使彼此相互区分的 core。除无状态代理以外，core 都是事务用户。虽然 UAC core 与 UAS core 的行为取决于方法，但所有方法都有一些通用规则（§8）。对 UAC 而言，这些规则管的是请求的构造；对 UAS 而言，管的是请求的处理与响应的生成。由于注册在 SIP 中扮演重要角色，处理 REGISTER 的 UAS 被赋予一个专门名称：注册服务器。§10 描述 REGISTER 方法下 UAC 与 UAS core 的行为。§11 描述 OPTIONS 方法下 UAC 与 UAS core 的行为，该方法用于探明 UA 的能力。

某些其他请求是在对话内发送的。对话是两个用户代理之间一段时间内持续存在的对等 SIP 关系。对话便于消息排序，并便于在用户代理之间正确路由请求。INVITE 方法是本规范定义的唯一建立对话的方式。当 UAC 发送一个处于某对话上下文内的请求时，它遵循 §8 讨论的 UAC 通用规则，同时还要遵循对话内请求的规则。§12 讨论对话，给出对话的构造与维护流程，以及对话内请求的构造。

SIP 中最重要的方法是 INVITE，用于在参与者之间建立会话。会话是一组参与者、以及他们之间用于通信的媒体流。§13 讨论会话如何发起，其结果是一个或多个 SIP 对话。§14 讨论如何在对话内使用 INVITE 请求来修改该会话的特性。最后，§15 讨论会话如何终止。

§8、§10、§11、§12、§13、§14 与 §15 的流程完全针对 UA core（§9 描述的取消同时适用于 UA core 与 proxy core）。§16 讨论代理元素，它便于在用户代理之间路由消息。
