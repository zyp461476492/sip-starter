SIP 鉴权框架与 HTTP（RFC 2617 [17]）几乎一致。具体而言，auth-scheme、auth-param、challenge、realm、realm-value 与 credentials 的 BNF 完全相同（但不允许把 `Basic` 当作 scheme 使用）。在 SIP 中，UAS 用 401 (Unauthorized) 响应挑战 UAC 的身份。此外，注册服务器与重定向服务器 MAY 使用 401 (Unauthorized) 响应做鉴权，但代理 MUST NOT，代理 MAY 改用 407 (Proxy Authentication Required) 响应。各类消息中是否需含 Proxy-Authenticate、Proxy-Authorization、WWW-Authenticate 与 Authorization，要求与 RFC 2617 [17] 所述相同。

由于 SIP 没有规范化根 URL（canonical root URL）这一概念，保护空间（protection space）的含义在 SIP 里解释得不同：仅由 realm 字符串定义保护域。这是对 RFC 2543 的一处改动——在 RFC 2543 里，Request-URI 与 realm 共同定义保护域。

> 旧的保护域定义造成了不少混乱：UAC 发出的 Request-URI 与发起挑战的服务端收到的 Request-URI 可能不同，而且 Request-URI 的最终形态甚至可能 UAC 并不知道。另外，旧定义依赖 Request-URI 里存在 SIP URI，似乎把其他 URI scheme（例如 tel URL）排除在外。

要对收到的请求做鉴权的用户代理或代理服务器，其运营者 MUST 遵守下列为服务器构造 realm 字符串的准则：

- realm 字符串 MUST 全局唯一。RECOMMENDED 的是：按 RFC 2617 [17] §3.2.1 的建议，realm 字符串含一个主机名或域名。

- realm 字符串 SHOULD 给出一个可读、可呈现给用户的标识。

例如：

```
   INVITE sip:bob@biloxi.com SIP/2.0
   Authorization: Digest realm="biloxi.com", <...>
```

一般来说，SIP 鉴权只对某个特定的 realm（一个保护域）有意义。因此对 Digest 鉴权而言，每个这样的保护域各有自己的一套用户名与密码。若服务端对某个请求不要求鉴权，它 MAY 接受一个默认用户名 `anonymous`，它没有密码（密码为 `""`）。同样地，代表大量用户的 UAC（例如 PSTN 网关）在本 realm 内 MAY 使用自己设备专用的用户名与密码，而不是为具体用户开账号。

虽然服务端可以正当地挑战大多数 SIP 请求，但本规范定义的两个请求在鉴权上需要特殊处理：ACK 与 CANCEL。

在"用响应携带用于计算 nonce 的值"（如 Digest）的鉴权方案下，任何不产生响应的请求（包括 ACK）都会带来一些问题。为此，服务端在 INVITE 中已接受的任何凭据，它 MUST 也为对应的 ACK 接受。UAC 生成 ACK 消息时，会复制该 ACK 所对应 INVITE 中出现过的所有 Authorization 与 Proxy-Authorization 头域值。服务端 MUST NOT 试图挑战 ACK。

虽然 CANCEL 方法确实会收到响应（一个 2xx），但服务端 MUST NOT 试图挑战 CANCEL 请求——因为这些请求无法重新提交。一般来说，若 CANCEL 请求来自发出被取消请求的同一跳（前提是存在 §26.2.1 描述的某种传输层或网络层安全关联），服务端 SHOULD 接受它。

UAC 收到挑战时，若该 UAC 设备并不知道所涉 realm 的凭据，它 SHOULD 把挑战中 `realm` 参数的内容（该参数出现在 WWW-Authenticate 或 Proxy-Authenticate 头域里）呈现给用户。一个预先给 UA 配好本 realm 凭据的服务提供商应当意识到：在预配置的设备上被挑战时，用户将没有机会提交自己的凭据。

最后要注意：即使 UAC 能找到与正确 realm 关联的凭据，这些凭据仍可能已经失效，或挑战方服务端因某种原因不接受它们（尤其在提交无密码的 `anonymous` 时）。这种情况下，服务端可以再挑战一次，也可以回 403 Forbidden。UAC MUST NOT 用刚被拒绝的那些凭据重试请求（不过若 nonce 已过期，请求可以重试）。
