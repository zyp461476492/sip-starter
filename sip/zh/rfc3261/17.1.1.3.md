本节规定客户端事务内所发 ACK 请求的构造。若由 UAC core 为 2xx 生成 ACK，则 MUST 改按 §13 的规则处理。

客户端事务构造的 ACK 请求，其 Call-ID、From 与 Request-URI 的取值 MUST 等于客户端事务交给传输层的那个请求（称其为“原请求”）中相应头域的取值。ACK 里的 To 头域 MUST 等于它所确认的那个响应里的 To 头域，因此通常会因为多出 tag 参数而与原请求里的 To 头域不同。ACK MUST 含单个 Via 头域，且该头域 MUST 等于原请求的顶层 Via 头域。ACK 里的 CSeq 头域，其序列号 MUST 与原请求中相同，但 method 参数 MUST 等于 `ACK`。

若被确认响应所对应的 INVITE 请求带 Route 头域，则这些头域 MUST 出现在 ACK 里。这是为了确保 ACK 能经任何下游无状态代理被正确路由。

虽然任何请求都 MAY 带消息体，但 ACK 里的消息体很特殊——因为即使消息体不被理解，该请求也无法被拒绝。因此，在针对非 2xx 的 ACK 里放消息体是 NOT RECOMMENDED；若真要放，消息体类型限定为曾在那个 INVITE 里出现过的类型（前提是对该 INVITE 的响应不是 415）。若响应就是 415，则 ACK 里的消息体 MAY 是那个 415 的 Accept 头域里列出的任何类型。

例如，考虑下面这个请求：

```
   INVITE sip:bob@biloxi.com SIP/2.0
   Via: SIP/2.0/UDP pc33.atlanta.com;branch=z9hG4bKkjshdyff
   To: Bob <sip:bob@biloxi.com>
   From: Alice <sip:alice@atlanta.com>;tag=88sja8x
   Max-Forwards: 70
   Call-ID: 987asjd97y7atg
   CSeq: 986759 INVITE
```

针对该请求的非 2xx 最终响应，其 ACK 请求如下：

```
   ACK sip:bob@biloxi.com SIP/2.0
   Via: SIP/2.0/UDP pc33.atlanta.com;branch=z9hG4bKkjshdyff
   To: Bob <sip:bob@biloxi.com>;tag=99sa0xk
   From: Alice <sip:alice@atlanta.com>;tag=88sja8x
   Max-Forwards: 70
   Call-ID: 987asjd97y7atg
   CSeq: 986759 ACK
```
