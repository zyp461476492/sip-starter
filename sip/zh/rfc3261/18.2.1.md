服务端 SHOULD 准备好在自己对外公布、供别人与自己通信的 SIP 或 SIPS URI [4] 上——凡是该 URI 经 DNS 查询可能得到的 IP 地址、端口与传输组合，都要能收到请求。这里的"对外公布"，包括把 URI 放进 REGISTER 请求或重定向响应的 Contact 头域，或放进请求/响应的 Record-Route 头域。URI 也可能通过放在网页或名片上被"公布"。同样 RECOMMENDED 的是：服务端在所有公共接口上监听默认 SIP 端口（TCP 与 UDP 的 5060，基于 TCP 的 TLS 的 5061）。典型例外是私有网络，或同一主机上跑多个服务端实例。凡服务端为 UDP 监听过的端口与接口，它 MUST 也在同一端口与接口上监听 TCP。原因是消息过大时可能需要改用 TCP 而非 UDP 发送。反过来并不成立：服务端不必因为已在某地址端口监听 TCP 就也在那里监听 UDP——当然，也可能有别的理由让它在某地址端口监听 UDP。

当服务端的传输层在任何传输上收到一个请求时，它 MUST 检查顶层 Via 头域值里 `sent-by` 参数的值。若 `sent-by` 的 host 部分含域名，或含的 IP 地址与包的源地址不同，服务端 MUST 在该 Via 头域值上添加一个 `received` 参数。该参数 MUST 含收到该包时的源地址。这样做是为了帮服务端的传输层把响应发回去——响应必须发往请求所来自的源 IP 地址。

设想服务端传输层收到的一个请求，部分内容如下：

```
   INVITE sip:bob@Biloxi.com SIP/2.0
   Via: SIP/2.0/UDP bobspc.biloxi.com:5060
```

该请求的源 IP 地址是 192.0.2.4。在把请求往上交之前，传输层添加一个 `received` 参数，于是该请求部分内容变成：

```
   INVITE sip:bob@Biloxi.com SIP/2.0
   Via: SIP/2.0/UDP bobspc.biloxi.com:5060;received=192.0.2.4
```

接下来，服务端传输层尝试把该请求匹配到一个服务端事务，用的是 §17.2.3 描述的匹配规则。若找到匹配的服务端事务，请求就交给该事务处理。若找不到，请求就交给核心（core），由核心决定是否为该请求新建一个服务端事务。注意：当 UAS 核心对 INVITE 发出 2xx 响应时，服务端事务即被销毁。这意味着 ACK 到达时已没有匹配的服务端事务，按此规则，ACK 被交给 UAS 核心处理。
